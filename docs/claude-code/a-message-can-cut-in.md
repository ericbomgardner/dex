# A message can cut in (CLI v2.1.314, SDK 0.3.314)

Probes: `Sidecar/test/writing-call-probe.ts` for a cut into a call being written; `Sidecar/test/now-priority-probe.ts` — the same interjection sent plain and with `priority: "now"`, into a streaming reply, a 20s foreground Bash and a foreground agent, plus the host's plain send with `backgroundTasks`, the host's send as it is now: `backgroundTasks`, then `"now"`, and both again a second into a Bash held by a 5s PreToolUse hook, and the host's in auto mode.

An `SDKUserMessage` takes `priority: "now" | "next" | "later"`. Unset, the CLI files it as `"next"`. What `"now"` does on its own depends on what the session is doing:

- **Streaming a reply**: the reply is cut off within about 30ms, the cut step ends with a `result` of its own (`success`, no `stop_reason`), and the message runs as an ordinary turn (`enqueue`, a bare `dequeue`, then a user turn). The partial reply stays in the transcript. The model answers and then picks the cut work back up by itself. One run on 2.1.283: answered in 7s against 23s for a plain send into a 400-line reply.
- **Running a foreground Bash**: nothing. The command runs to its last line and the message waits for it like a plain send does.
- **Running a foreground agent**: the agent is killed. Its call returns `[Request interrupted by user for tool use]` and its task settles `stopped`. Still true on 2.1.283.

**The host sends every message to a working session as `backgroundTasks()`, then `"now"`** (`HostedSession.send`, `#cutIn`). That is what the terminal's send-now became in CLI v2.1.281 ("move running tools to the background instead of cancelling the turn"), but the change is in the terminal, not the SDK's `"now"`: `"now"` alone still kills an agent. Backgrounding first leaves nothing foreground for it to kill. Measured on 2.1.283:

- a foreground agent: moved to the background (its call comes back as the async launch receipt), the message answered in 1.4s, and the agent runs on to `completed`;
- a foreground Bash: moved, answered in about 9s with the command still running;
- a streaming reply: cut, as above.

**Order is load-bearing**: the send waits for `backgroundTasks()` to answer, and cut-ins are chained so two quick sends keep their order across that wait. A plain send while the session isn't `running` is unchanged, and so is `asking`: nothing done to tasks unparks an ask.

**A cut throws away every call in the reply it cuts** (CLI v2.1.312, `Sidecar/test/writing-call-probe.ts`). Sent while the model was still writing a background Agent call, `"now"` ended the reply within 15ms with an `error_during_execution` result, and the half-written call never launched and got no result at all. In a real session (2026-10-30), calls already written in the same reply came back `Error calling tool (Agent): ` with nothing after the colon, three times in a row, each at the millisecond the user's message landed. A brief takes 20s and more to write, so this is a wide window, not a race. So **the host holds a cut-in for as long as the reply streaming has started a call**: from the call's `content_block_start` to `message_stop` (`#replyHasCall`, `#replyWritten`), read off partial messages ([What a reply is writing](what-a-reply-is-writing.md)). Then it backgrounds and cuts in as usual. Measured: held this way, the call launched and the message was answered 6.2s after it was sent; a plain send also saved the call, answered in 7.9s. The hold is checked again after `backgroundTasks()`, since a call can start during that wait. The reply's tool results end the hold too, so a stream that never says `message_stop` doesn't hold a send through every tool it ran. A reply that was writing an `AskUserQuestion` or `ExitPlanMode` releases the send plain, not `"now"`: the session is about to park on it, and a send to an asking session goes in plain (unprobed what `"now"` does in that gap).

**A cut also throws away a call that hasn't started running** (CLI v2.1.314, `now-priority-probe.ts`). Between being written and running, a call waits on its PreToolUse hooks and, in auto mode, the classifier: seconds that from outside look like a running command, with no task and no result. `backgroundTasks()` has nothing to move, and `"now"` sent then ends the call. Behind a 5s hook it came back `The user doesn't want to take this action right now…` 13ms after the send; in a real auto-mode session on 2026-10-31, a message 3.8s after a Bash call came back `<error>Command was aborted before completion</error>`, and the command never ran. Once it is running, the same send leaves a Bash alone. How long the classifier takes varies (under a second to several), which is why the probe pins the window with a hook. So **the host also holds a cut-in while a call from the main reply has neither a task nor a result** (`#callsStarting`, `#callsSettled`): a long Bash is announced as a task about 3.5s after it starts, an agent at once, and anything shorter has its result by then. It backgrounds once before the hold as well: a call queued behind a foreground Bash starts only when the Bash is out of the way. A call whose task was announced before its block arrived isn't counted. Then it backgrounds and cuts in as before. `AskUserQuestion` and `ExitPlanMode` aren't counted: they wait on the user, and a send to an asking session goes in plain anyway. A long call that never becomes a task, an MCP tool or a `WebFetch`, now holds the message until it returns, which is what a plain send did.

What it cost: a message can no longer be taken back. The CLI takes a `"now"` message within about 30ms, so the unsend request, `cancelAsyncMessage`, and the pane's take-back were removed with this change. A cut also ends a step with a `result`, so the host goes `idle` and back to `running` between the cut and the answer, the same flicker two queued turns always had.

Why real sessions waited before: messages over 1s from enqueue to take, in real transcripts, were either the model mid-step (a median of about 5s) or behind a foreground command sent into before it was announced as a task. The first is what the cut fixes; the second is the retry on `task_started` (see [A message can take the turn back from a foreground task](a-message-can-take-the-turn-back-from-a-foreground-task.md)), still needed because `"now"` does not cut a Bash.

Probe caveats: closing a session kills a backgrounded command, so the probe only checks the Bash's last line for the runs that leave it in the foreground. Answers are timed off the first streamed delta carrying the word, not the finished message: a `"now"` answer goes on with the cut reply in the same block, and timed off the message it reads as slow as the reply.

Code: `HostedSession.send`, `HostedSession.#cutIn`, `#replyWritten`, `#callsSettled`, `PushStream.push`.
