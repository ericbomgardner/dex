# A subagent's report arrives as a message, not in its result (CLI v2.1.300, SDK 0.3.300)

Probe: `Sidecar/test/handback-probe.ts` — four sessions: a foreground agent, a background agent reporting to a busy parent, one reporting to an idle parent, and one that backgrounds its own work.

**Auto mode only.** In `auto` the agent calls a `SubagentHandback` tool with its report; in `bypassPermissions` the report is in the result and the tool is never called. The app sends `auto` on every start.

**The parent's Task result is a stub**: `This agent's report was delivered to you as a message from "<agentId>" (its SubagentHandback call). Read it there; it is not repeated here.`, with a `<usage>` under it in colon form (`subagent_tokens: 85650`). `toolUseResult` still carries `agentId` and the three counts (plus `handback: "send"` and unread `harness*` keys), and a background agent's `<task-notification>` still carries the tagged `<usage>` with the stub under `<result>`, so the tally and settling in [Subagent results](subagent-results.md) are untouched. **`TranscriptText.totals` cannot read the colon form** and doesn't need to while the counts sit beside the result; the day the notification's `<usage>` takes that form, background tallies go blank silently.

**The report lands as a peer message.** To a busy parent, the absorbed shape: `enqueue`, a `queued_command` attachment with `commandMode: "prompt"` and `isMeta: true` (on the attachment, not the record), `remove` with `absorbed_mid_turn`. To an idle parent, the peer door: `enqueue`, `dequeue`, then an `isMeta` **user** record with plain-string content, `origin` at the top level plus `turnOrigin: "peer"`, and the CLI's `Another Claude session sent a message:` preamble — and **the parent runs a turn on it**, so the row moves with nobody at the keyboard. Either way `origin` is `{kind: "peer", from, senderTaskId, name, body, handback: true}`, sometimes `flagged: true` (unread). Both doors go through `peerMessage`.

Two differences from a session's peer message, each of which breaks something quietly:

- **`name` is the agent's type** (`general-purpose`), not a messaging name — absent until CLI 2.1.286. `from` and `senderTaskId` are the agent id, and only the id tells two agents apart. Nothing reads this `name`: both readers drop a hand-back on `handback` before they look at it, and `RawOrigin` reads `handback` and nothing else new.
- **The wrapper is `<agent-message from="…">`**, not `<cross-session-message>`. If `cleaned` leaves it whole, `isPeerMessage` says no and the enqueue counts in `heard` as something you typed — which retires the stand-in for a message you actually sent. `peerMessage(unwrapping:)` reads both wrappers.

**The report is not drawn in the main transcript.** It is addressed to the parent, and the same text is already the tail of the agent's own conversation under the delegation row. `peerMessage` drops a hand-back on both doors and moves no clock for it, where an ordinary peer's message on the same door still becomes a turn.

**The body is framed on purpose**: it opens `[Subagent hand-back] … The report follows:`, sometimes carries a `[harness: …]` line, and indents the whole report two spaces so a frame-shaped line at column zero can be told from a forged one. `TranscriptText.handbackReport` strips the frame and the indent; a body that doesn't open with the frame passes through untouched, so an ordinary peer message is never dedented.

**The agent's own file ends on the call**: `tool_use: SubagentHandback` with the report under `input.message`, a `{"success":true}` result, then one line of text. `ToolCall.isHandback` draws it as the outbound half of the exchange, the way `SendMessage` is, and as markdown — it is the one place the report is read.

**A `completed` notification is not always the report.** An agent that backgrounds its own work ends its turn without calling `SubagentHandback`. Since 2.1.299 the parent hears twice. First a notice naming the call, `completed`, summary `Agent "…" is waiting on its own background work`, and a `<note>` ending "the result below may be interim", with the tally so far. Then, when the agent is really done, a notice with the whole run's tally that **names only the task**: no `<tool-use-id>`, and a `<note>` saying the same task id may notify again if the agent is resumed. Both readers skipped a notice without a call, so the row kept the interim tally for good. Now `bringAgentsBack` remembers the task id of an interim notice and lands the next notice for that task on the same call (`interimAgents`); a notice that isn't interim forgets it. A notice naming only a task with no interim one before it still settles nothing, as a Monitor's event never should. Unmeasured: whether an agent resumed by `SendMessage` notifies the same way.

Probe caveats: the idle run's agent must be slow and hold its wait in the foreground, or it beats the parent to the end of the turn and the two doors collapse into one; and the `remove` is matched on the `<agent-message` wrapper, never on `absorbed_mid_turn`, which a background agent's `<task-notification>` shares.
