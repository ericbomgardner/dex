# Compaction (CLI v2.1.316, SDK 0.3.316)

Probe: `Sidecar/test/compaction-probe.ts` — one session, four turns then `/compact`, then a resume whose first prompt is `/compact`; pins the stream order, what the compacted conversation holds, and the badge-vs-`postTokens` gap.

**The records.** A `/compact` — and, by the same record, an automatic one — is written as five records, in this order:
1. a `system` record, `subtype: "compact_boundary"`, with `compactMetadata` (`trigger`, `preTokens`, `postTokens`, `durationMs`);
2. a `user` record marked `isCompactSummary: true`, the summary as a plain string, opening "ran out of context" whether or not it did;
3. the `isMeta` caveat;
4. the typed `/compact` as a `<command-name>` turn;
5. its `<local-command-stdout>` (`Compacted`, possibly wrapped in ANSI dim escapes).

**Read in file order.** The summary lands above the command that asked for it, and timestamps make it worse: the command's is older than the boundary's, and the summary's is milliseconds older than the boundary it is chained under. **Key off the boundary, never the command turn** — an automatic compaction writes no command.

Reader: the boundary is a `.system` entry holding a `Compaction` block; the summary folds onto it (`TranscriptDocument.summarised`) and draws collapsed under `CompactionDivider`; `TranscriptFlow.heard` skips it. Read naively, the boundary is dropped (no role), the summary draws as prose you typed, the handover clock goes back to the compaction, and the summary counts toward what the composer is waiting to hear.

**`postTokens` is not the badge's number, but it is what the badge shows after a boundary, marked `~`.** `postTokens` counts the conversation kept; the badge counts what the next request sends, which adds the system prompt and tool schemas (a ~18k floor on 2.1.314, ~21k before). At small sizes they differ several times (3,166 against 19,010 on 2.1.314); at 500k → 5k the floor is noise, and a badge that waits for the next assistant turn sits at the old size indefinitely, since a `/compact` writes no assistant turn. So `TranscriptDocument.compacted` and `SessionDigestReader` set `SessionContext(isEstimate: true)` from `postTokens`, drawn `~5.1k ctx`, and the next assistant turn replaces it with the exact reading ([What a session is carrying](what-a-session-is-carrying.md)). The pair still goes on the divider as the CLI's own words. Don't estimate from the pre-compaction badge minus the drop: `preTokens` is on a different scale and the arithmetic goes negative.

**The `/compact` line is on no drawn record for the whole compaction** without `TranscriptDocument.taken`: its stand-in comes down on the `enqueue`, its queue row goes on the `dequeue`, and the command turn is only written when the compaction ends. `taken` holds what was dequeued until the next non-queue record, drawn at full weight while the session is working.

**The stdout record answers the command.** The CLI writes no assistant turn for a local command, so `TranscriptStanding.owesTurn` used to read the `/compact` turn as an unanswered message and spin the row for the rest of the file. A `<local-command-stdout>` at the end reads as nothing owed — the same rule covers `/cost` and every other local command.

**The live word is socket-only.** The SDK sends `system/status` with `status: "compacting"`, then `status: null` with `compact_result`, a fresh `system/init`, and a `result` closing the turn — all **before** the boundary lands, so a client that stops reading when the spinner clears drops the only record carrying the new size. The host forwards the stretch as `compacting` (`SessionState`, `HostSessionState.compacting`): working in the list, `Compacting…` on the row and the pane's working line. `SessionRowModel.isCompacting` exempts it from the 15s quiet-dim, since nothing is written to the file for the whole stretch. A host older than the state never says it.

**A resume told `/compact` first says nothing else until it is done.** Its first message is `status: "compacting"`; `system/init` comes only after `status: null`, before the boundary. The app counts a resume as up on `session.init` and gives up after 90s, and a 964k window took 114s to compact, so the resume was reported failed while it worked, the typed `/compact` was put back in the composer, and the row had no state to show. The host now sends `session.init` on a resume's first message of any kind, under the resume id with model and commands still nil, and the CLI's own `init` fills them in when it comes. The probe's last section pins the order.

**Since 2.1.304 the skill list is sent again after a compaction**, as a `skill_listing` attachment after the stdout record and before the next prompt, alongside the agent, deferred-tool and MCP listings that already followed. It rides in `postTokens` (~1.5k more than on 2.1.303) and in the badge, so a conversation of a few thousand tokens compacts to about its own size and the badge can read higher after than before. Nothing in the app assumes a compaction lowers the badge; the probe fills ~10k of conversation so its "less than before" check still measures a drop.

**What survives a compaction is the summary and the newest reply, verbatim.** The boundary names that reply as `logicalParentUuid` and in `compactMetadata.preservedMessages` (`preservedSegment` too, and `cumulativeDroppedTokens` beside `postTokens`); it stays where it was in the file, above the boundary, and the next request sends the summary then that reply word for word. This has been so since at least 2.1.268. The summary is written without seeing the kept reply and ends by saying so ("kept verbatim… written without seeing them"). So the model answers the last prompt again inside the summary, and when the last reply is the bulk of the conversation it is carried twice.

**Since 2.1.311 a summary reply with no `<summary>` block is asked for once more** (changelog: "asks for the summary once more before it replaces the conversation"; the "no <summary> block, asking for the summary once more" string is in the 2.1.311 binary and not in 2.1.304's). On 2.1.283 haiku's re-answer was taken as the whole summary (~3k chars). On 2.1.314 the summary is the re-answer plus a structured `Summary:` section, ~10k chars on the probe's old fill, and `postTokens` went from ~3k to ~7k. With the old fill's bulk in its last reply the badge read the same after as before: 25,293 → 25,402, and 25,089 → 24,997 on a rerun. **A compaction lowers the badge only when the history before the newest reply outweighs the summary plus that reply.** Nothing in the app assumes it does. The probe puts its bulk in the first three turns and ends on a one-line one, so its "less than before" check still measures a drop (27,937 → 19,010).

**On 2.1.314 the summary string opens with a reminder block** after its first line: a `system-reminder` holding `tools-used-before-summary`, which names tools such as `SubagentHandback` and `Monitor`, or nothing at all. On 2.1.268–2.1.283 the summary was plain. `TranscriptDocument.summarised` removes that one block, and `transcript-render.py`'s `_summarised` does the same. Any other tag the summary quotes is kept, so `TranscriptText.cleaned` isn't used here.

Probe caveat: compaction counts message groups, not tokens. One fat turn answers `compact_result: "failed"`, `Not enough messages to compact.`, and writes nothing — which reads exactly like a compaction that ran and broke. Fill three turns first. Haiku sometimes answers a fill prompt with a bare list, so the probe checks the fill put 4k above the floor before it reads the drop.
