# Reconnecting and logging in to an MCP server (CLI v2.1.296, SDK 0.3.296)

Probe: `Sidecar/test/mcp-actions-probe.ts` — one short haiku turn against an http server that starts listening after it, and an http server behind a fake OAuth authorization server. `Sidecar/test/mcp-reconnect-config-probe.ts` — a project `.mcp.json` server whose port is changed in the file mid-session, and a `HostedSession` left to reconnect a late server by itself.

The MCP chip's popover (`McpTroubleChip`) offers Reconnect for a server that failed or stopped responding and Log In for one that reads `needs-auth`. The host runs both (`mcpReconnect`, `mcpLogin`, capability `mcp`), and only for a session it holds; for any other session the popover offers Open Settings.

- **`reconnectMcpServer(name)` is typed and takes effect at once.** A server that read `failed` reads `connected` on the next `mcpServerStatus()` once something listens, with no turn between. The CLI never retries a failed server on its own. A name it doesn't know throws `Server not found: <name>`. A server that is still down throws the same `ECONNREFUSED…` text a call would, and its status flips to `failed`. So the host reads the status again after every reconnect, whether it worked or not.
- **`reconnectMcpServer` reads the server's config again.** With `.mcp.json` rewritten to a new port, a reconnect connects to the new one. `mcpServerStatus()` keeps reporting the URL the session started with until a reconnect runs, failed or not. Checked with a project `.mcp.json`; `~/.claude.json` was not touched, so its user and local scopes are assumed to load the same way.
- **The host retries a server that failed to connect** (`#retryMcp`), for a session it holds. Only `http` and `sse` servers that read `failed` with a connection-level error (an error that starts with `ECONNREFUSED` or another socket code; `mcpRetryTarget`) qualify. Not `needs-auth`, stdio, or a server that answered: a 404 reads `MCP endpoint not found at <url>. Check the URL in your MCP config.` It opens a TCP connection to the URL's host and port 5s after the reading, doubling to a minute, and reconnects once one opens, then reads the status again. Because the status's URL can be stale, it also reconnects every five minutes whatever the knock says. Retries are never emitted, so they don't keep a session from the reaper, and they end when it's stopped or reaped.
- **Reconnecting a server that reads `connected` resolves.** This is the only fix for a drop read off the transcript ([An MCP server that drops says so only in its calls](an-mcp-server-that-drops-says-so-only-in-its-calls.md)), whose status never moved. The drop stays the newest call until another call is answered, so the app remembers the drop each reconnect was pressed on, by the transcript's own timestamp, and hides that drop and older ones. It never compares against its own clock.
- **`mcpAuthenticate(name, redirectUri?)` is on the `Query` at runtime but missing from `sdk.d.ts`.** With no redirect URI it answers `{authUrl, requiresUserAction: true, callbackExpected: true, redirectScheme: "localhost", state, callbackPort}`, after doing discovery and dynamic client registration itself. The CLI listens on `localhost:<callbackPort>`. Once the browser's redirect reaches it, the CLI trades the code for a token and the server reads `connected` within about 250ms, with no reconnect. The host polls the status every 5s for up to five minutes after each login, until that server connects (`#mcpLogins`, one deadline per server).
- **The token is stored in the user's real credential store.** The probe clears it with `mcpClearAuth(name)`, also missing from `sdk.d.ts`.
